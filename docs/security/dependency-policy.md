# Dependency Security Policy

The durable record of dependency security decisions. PR threads disappear from
view; this file is what keeps the reasoning available and the judgement consistent
over time.

## Policy Summary

| Topic | Rule |
|-------|------|
| Update bot | Renovate only. Dependabot security updates are disabled; advisories arrive through `osvVulnerabilityAlerts` |
| Cooldown | 7 days for npm packages, inherited from the shared preset; none for known-CVE fixes |
| Merge criterion | `no-runtime-impact` label **and** every required check green. Both required |
| Who may merge | The `dep-triage` routine only. Renovate automerge is disabled everywhere |
| Automated merge scope | Only `no-runtime-impact` classes: `@types/*`, GitHub Actions, lint tooling, test tooling |
| Blocking scan | Trivy, production dependencies only, CRITICAL and HIGH |
| Non-blocking scan | Trivy with `--include-dev-deps`, report only |
| Suppression | Requires `statement` and `expired_at`, maximum 90 days |
| Merge to `main` | Always a human action |

## Triage Decision Tree

Every finding resolves to exactly one outcome. "Leave it open" is not one of them.

```text
New finding (Trivy / OSV / CodeQL)
  |
  +-- Is a fixed version available?
  |     |
  |     +-- Yes -> Is it a direct dependency?
  |     |            +-- Yes -> bump the dependency          -> [FIX]
  |     |            +-- No  -> add a pnpm.overrides entry   -> [FIX]
  |     |
  |     +-- No  -> Is the vulnerable code path reachable in production?
  |                  +-- Yes -> open an issue, label security  -> [ESCALATE]
  |                  +-- No  -> .trivyignore.yaml,
  |                             statement + expired_at (90d)   -> [SUPPRESS]
  |
  +-- Does the fix require a major upgrade or an API change?
        +-- Yes -> open an issue, do not attempt automatically -> [ESCALATE]
```

- `[FIX]` - bump the dependency, or pin the transitive version via `pnpm.overrides`
- `[SUPPRESS]` - record in `.trivyignore.yaml` with a reason and an expiry
- `[ESCALATE]` - open an issue; the fix needs human judgement or an API change

### Reachability criteria

A finding counts as **not reachable in production** only when at least one of these
holds, and the reason is written into `statement`:

- The package is a build-time or test-time tool and does not ship in the Workers bundle
- The vulnerable API is called nowhere in the repository, verified by search
- The vulnerable path requires an input the application never supplies, such as a
  parser reached exclusively with fixed internal input

Anything reaching the Workers runtime with request-derived input is reachable, and
`[SUPPRESS]` is not available.

### Suppression limits

- Maximum expiry is 90 days. Anything longer is a human decision, recorded below
- A suppression may not be renewed twice in a row automatically. On a second
  renewal, escalate to an issue instead

## Version Pins

`pnpm.overrides` in the root `package.json` pins transitive versions where a direct
bump is not possible. New pins are generated by Renovate rather than written by
hand.

Pins are reviewed for removal whenever the resolved tree already satisfies the
constraint without the override. Removals are verified with `pnpm tsc` and both
test suites, and are never bundled with an unrelated change.

```text
### YYYY-MM-DD <advisory-id> <package>

- Outcome: [SUPPRESS] | [ESCALATE]
- Reason: why the vulnerable path is or is not reachable
- Evidence: what was checked, such as a search for the vulnerable API
- Follow-up: expiry date, or the issue tracking the fix
```
